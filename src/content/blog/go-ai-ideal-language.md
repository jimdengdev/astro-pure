最近读到公众号「Go语言中文网」的一篇译文《Google 官方说 Go 是 AI 编程的最佳语言，让你认同吗？》，它转述的是 Google 开发者博客 2026 年 8 月 11 日由 Go 产品负责人 Cameron Balahan 和 Google Cloud 首席布道师 Richard Seroter 联名撰写的长文。这篇文章在 Hacker News 上吵了几百条评论，支持和反对都很激烈。我 Go 和 Python 都在用，读完有点想法，记下来。

## 一、它说得对的地方：瓶颈真的从「写」挪到了「审」

最核心的那句判断我完全认同：当 AI 几秒就能产出几百行语法正确的代码，「写得多快」就不再是衡量语言生产力的标准，真正稀缺的是人的审查、验证和维护成本。这个转变其实比语言之争更重要——它是在重新定义「什么语言算好语言」。原文作者甚至给出一个体感数字，说他审 Go 代码的速度大约是 Python 的 2～3 倍；我提醒自己这只是「体感」，不是实测，但这个方向我相信是对的。

在这个前提下，Go 的几件事确实是真优势，不是吹出来的：

- **工具链一体化**。`gofmt`、`go test`、`go mod`、`go vet`、`govulncheck`、`pprof`、`gopls` 全是官方内置，团队不用先开会决定用 Black 还是 autopep8、用 pytest 还是 unittest。对 AI agent 来说，这少掉了一整层「猜项目约定」的不确定性。
- **静态类型 + 极快编译 = 自我纠正闭环**。方法名拼错、类型不匹配、变量没用，编译器当场拒绝，AI 在交给人类之前就把这类错修掉了。
- **单一格式带来的可读性**。不管谁写的 Go 都长得差不多，审查时省去「先适应它的风格」的开销。

里面我尤其喜欢 `govulncheck` 的设计：它做可达性分析，只报告你实际调用到的漏洞函数，不报无关版本号。这种「低噪音、可操作」的反馈，才是自动化流程真正能用的东西。

## 二、但「理想语言」这四个字，说大了

以下是我的保留意见。

**1. 编译通过 ≠ 正确。** Go 的类型系统能挡住拼写和类型错，挡不住业务逻辑错。批评者的火力更集中：Go 允许 nil 指针、允许结构体部分初始化，编译器拦不住无效状态；而「AI 生成 + 人类验证」模式下，这恰恰是最危险的。Rust、Haskell 靠更强的类型系统能在编译期多挡一层。Go 的取舍是「简单优先、牺牲部分静态保证」——这是优点，也是代价。

**2. 优势有场景边界。** Go 的强项集中在 AI agent 运行的基础设施、后端服务、CLI 工具这一带；如果任务本身是「构建 AI 应用」——调大模型 API、接 AI SDK、做数据科学——Python、TypeScript 的生态厚度是 Go 追不上的。有个很具体的对比：Python 生态里有 2500 多个活跃维护的 AI/机器学习库，Go 只有不到 300 个。所以结论更像「Go 特别适合 AI 辅助的后端与基础设施开发」，而不是笼统的 ideal for AI-assisted software engineering。

**3. 训练数据量这个变量被轻轻带过了。** LLM 生成代码的质量，很大程度取决于训练语料里这门语言的公开代码规模，而 Go 在 GitHub 上的存量远不及 Python、JavaScript。不过这里也别走极端——有实测者说，Go 几乎瞬间编译，编译语言的摩擦力反过来逼着 LLM 产出更靠谱、更可读的代码。也就是说，结论可能既取决于语言，也取决于模型。

**4. 有些具体场景 Go 反而别扭。** 做 LLM 应用的人会懂：Go 没有 sum type、没有模式匹配，「模型返回的是工具调用、纯文本、拒绝、还是格式错乱」这类分支，在 TypeScript 的联合类型里写得很干净，在 Go 里得靠 type switch 加接口断言硬拼；而 LLM 输出恰恰是半结构化的，用 `encoding/json` 硬 marshal 进固定 struct 是最难受的场景。

**5. 立场问题。** Google 既是 Go 的创造者也是主要维护者，这篇文章首先是一份立场陈述，不是跨语言基准测试——它并没有证明在同一任务上 Go agent 犯的错更少。

## 三、我的结论

我不接受「最佳语言」这个说法，但我接受它揭示的那层真实变化：当代码生成的成本趋近于零，语法表达力就不再值钱，「无聊」的确定性、可读性和低成本验证开始值钱。

落到实践，我的三点建议：

- **别信口号，自己测。** 用同一个 agent 和 prompt，分别生成 Go 和 Rust（或 Python）实现，记录编译通过轮数、token 消耗、review 时长和测试通过率，各跑三次取中位数——单次实验噪声太大，而且结论只适用于你自己的场景。
- **语言只是工具，纪律才是护栏。** 少引入依赖能降风险，但安全还来自密钥管理、超时、鉴权、日志脱敏；语言可以降低出错概率，却不能替人决定哪些操作可以自动化、哪些必须停下来问。
- **最危险的默认假设**，是「因为 AI 写得快，我们仍按写得快来衡量生产力」。

Go 不是「恰好适合 AI」，更不是「唯一适合 AI」。它只是在一个特定场景里，把「人 + AI 协作」的设计成本压得比较低。这已经足够值钱了——但没必要被「理想」这个词绑架。
